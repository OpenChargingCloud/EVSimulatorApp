# EV Simulator App — Feasibility Study & Work Plan

A Capacitor app that simulates an electric vehicle speaking ISO 15118-2 and -20 against a
C# SECC counterpart (Raspberry Pi, WLAN instead of PLC).

Status: **concept**, with Track A partly executed. Written 2026-07-29; revised 2026-07-30, when
the Kotlin and Swift back ends went from *plan* to *code* and several of this document's
projections became measurements. Where that happened, the original wording is kept and the finding
is added next to it — the plan being wrong in a specific, dated way is more useful than a document
that has quietly always been right.

---

## 0. Executive summary

**Feasibility: yes, and much cheaper than expected — but not the way the task was framed.**

The decisive finding is that the submodules under `libs/` are not partial building blocks.
Together they are **a complete, externally-validated ISO 15118 stack, a security-research
toolkit, and a standardised dynamic-QR mechanism**:

- **`Vanaheimr.V2G.Exi`** — both protocols feature-complete at session level, 689 green tests,
  byte-exact against libcbv2g, cross-checked against EXIficient, and live-interop-proven against
  Josev in both directions including Plug & Charge, contract provisioning, pause/resume,
  renegotiation and signed tariffs. ~122k lines of generated codec, ~2.7k lines of state
  machines, plus a **pure-managed BouncyCastle TLS stack** doing the -20-faithful
  secp521r1/Ed448 mutual handshake.
- **`WWCP_ISO15118`** — the layers *below and beside* the codec: a real SLAC implementation
  (incl. a Qualcomm HomePlug chip controller, AF_PACKET transport and a **MitM bridge**), SDP,
  V2GTP, a **V2G PKI builder with a deliberate "Evil" certificate factory** (~14 attack
  variants), a 52k-LOC ISO 15118-20 domain model **with JSON serialisation**, and a curated
  security-research bibliography.
- **`DynamicQRCodes`** — the owner's own reference implementation of the **AFIR / OCPP v2.1
  dynamic QR-code** mechanism: TOTP generation (C#, JavaScript, Android) plus the standardised
  URL-template vocabulary. This is what makes the app's QR pairing a real proximity proof rather
  than a convenience (§4.6).

The second repo's material contribution is that the **certificate-breakage and
security-scorecard features stop being ideas and become integration work** (§7.1). Its
hand-written -20 JSON-LD model is *not* reused — the bridge format is **JSON-LD generated from
the XSD model** by a second emitter pass, for -2 and -20 alike (§4.4); WWCP's conventions survive
as style guidance.

The app's bootstrap concept is **QR pairing** (§4.5): one scan replaces plug-in + SLAC + SDP, and
the payload carries metadata — endpoint, transport, **crypto profile and its non-conformance
reason**, trust-anchor fingerprint — which is what makes the -20 TLS problem (§3.3) tractable.
The codes are **dynamic**, reusing the owner's own AFIR / OCPP v2.1 TOTP mechanism
(`OpenChargingCloud/DynamicQRCodes`, a third submodule). That is what makes the substitution
honest: a rotating code proves the EV had line-of-sight to the EVSE display *within the last
slot*, which is a **proximity proof** — the same class of guarantee SLAC actually provides, over
a different medium (§4.6).

### Architecture decision (2026-07-29): full native port

**Chosen: a full native port** — Kotlin and Swift reimplementations of the codec, XMLDSig,
state machines and transport, generated by retargeting the existing source generator. This was
my non-recommended option in the first draft; the owner chose it deliberately, and the reasons
hold up better than my initial caution did:

- **It removes the single scariest technical risk.** My first-draft 🔴 #1 was NativeAOT on
  Android (`linux-bionic`), an under-trodden path. A native port has no .NET runtime on the
  device at all, so that risk simply disappears.
- **The port has a free byte-exact oracle.** The generator's analysis half (~1,200 LOC,
  `Xsd/`+`Grammar/`) is language-neutral; only the emitter (~2,200 LOC) is C#-specific. Every
  ported codec is validated against the existing `Vectors/*.json` corpus, which is byte-exact vs
  libcbv2g. So the port is **a lot of known, parallelisable work with a ready checker** — not a
  research risk.
- **The Kotlin/TS EXI libraries are independently publishable** and useful to others; the C#
  core stays as the Pi-side counterpart and the reference oracle.

The honest cost, carried knowingly (see §2, §3.3): the whole stack is implemented **three
times** (C# reference + Kotlin + Swift), XMLDSig-over-EXI-fragments — "the hardest part of
15118" — twice more, and iOS needs an answer for the -20 TLS suites. That last one is the only
piece that does not fully dissolve; §3.3 gives the resolution, which the "real chargers are
out of scope" decision makes tractable.

A third emitter target, **TypeScript**, is arguably higher value than Swift: it puts the codec
in the same language as `ChargyCore.TS`, which is where the transparency-software endgame
lives, and it can run the codec directly in the Capacitor WebView.

#### Where the port actually stands (2026-07-30)

Two of the three back ends exist. **Kotlin** (102,668 lines across 782 files) and **Swift**
(89,670 lines across 669 files) both carry every message set the app needs, plus fragment codecs,
the signing layer, V2GTP and the payload dispatcher. TypeScript has not been started.

The two claims above that the work has since tested:

- *"The port has a free byte-exact oracle"* — **held.** 148 Swift vectors are byte-exact against
  libcbv2g, and no vector needed a Swift-specific allowance. But the oracle turned out to be
  **necessary and not sufficient**: it pins the encoder, and the decoder is then checked by
  round-tripping through that same encoder, so a bug mirrored in both directions passes. Four
  bugs of that kind were caught by the *cross-emitter* gate instead (§5, Track A note) — a gate
  this document counted as standing and which did not exist.
- *"Swift last, because it carries the one hard crypto gap"* — **abandoned, deliberately.** Swift
  ran second. The gap (§3.3) is real but sits in Ed448 alone, which turned out to be separable
  from the entire codec and even from -20's primary P-521 signing path. Sequencing the whole
  back end behind it would have been sequencing 89k lines behind a 114-byte signature.

Both requested features are well-supported:

- **Certificate management in the GUI** — the PKI model is already documented
  (`Vanaheimr.V2G.Exi/docs/pki-model.md`) and a BouncyCastle PKI builder — *including a
  deliberate-breakage "Evil" cert factory* — now ships as a submodule (`WWCP_ISO15118_PKI`).
- **EV-signed meter readings** — this is a real standard feature, not an extension:
  `MeteringReceiptReq` (-2) and `MeteringConfirmationReq` / `SignedMeteringDataType` (-20).
  Both are already implemented and live-tested in the C# stack.

And the Chargy endgame is better than expected: **it needs no vendor extension for the core
case.** `MeterInfoType.SigMeterReading` (-2) and `MeterInfoType.MeterSignature` (-20) are
standard fields carrying up to 64 bytes — exactly one raw ECDSA P-256 `r||s` signature. The
station can hand the EV a signed meter reading over stock ISO 15118 today. Only the *full*
transparency record (public key, meter serial, OCMF envelope) needs a carrier, and -20's VAS
mechanism is the right one.

**How the two repos relate.** Vanaheimr owns the *wire* (EXI, XMLDSig, V2GTP, session state
machines, TLS); WWCP owns *everything the wire sits on or is judged by* (SLAC/PLC, discovery,
PKI, attack material) plus an independent semantic model of -20. They overlap only in SDP and
V2GTP, and Vanaheimr already consumes `WWCP_ISO15118_PKI` for its test hierarchy — so the
intended split is already established, and this project should preserve it rather than merge.
**Where they overlap (SDP, V2GTP), the app uses Vanaheimr's** (decided 2026-07-29, §8);
WWCP's equivalents stay for Pi-side and security-research use.

### 1.3 Why this reframes the task

The original framing ("use the libs mainly for the EXI part, copy the generator") assumes the
EXI codec is the bulk of the work. It is not — it is the part that is *most* finished, and it
is finished *with external oracles*, which is the expensive kind of finished. The genuinely
expensive remaining work in any port is:

1. **XMLDSig over EXI fragments** — the roadmap calls it "the hardest part of 15118", and the
   repo carries a *dual-grammar* implementation (cbV2G-byte-exact combined form **and** Josev's
   standalone form) because real peers disagree. Reproducing that in Kotlin and Swift means
   reproducing ~15 conformance bugs' worth of hard-won knowledge.
2. **TLS with the CharIN profiles** — see §3.3.
3. **The ~15 real conformance fixes** found only by live interop, which are diffused across the
   state machines and will not announce themselves during a port.

A port therefore does not start from "4,000 lines of generator". It starts from "an entire
validated stack, minus its validation".

### 1.4 What is *not* there

- **No `EVSimulatorApp` code yet** — ⚠️ *out of date as of 2026-07-30.* The repo now carries
  `kotlin/` and `swift/` (Track A's first two back ends, §5). What is still greenfield is
  everything **above** the codec: no Capacitor scaffold, no plugin bridge, no UI, no state
  machines in either target language, and no Pi-side work (Track B in full).
- **No DIN SPEC 70121** — `WWCP_DINSpec` is an empty placeholder. Parked by decision (§6.1).
- **No ISO 15118-2 in WWCP** — irrelevant, Vanaheimr covers -2 fully; but it means the WWCP
  JSON model is **-20-only**, which matters for §4.4.
- No WPT/ACDP session state machines (codec only) — irrelevant for a phone.
- No AC DER session wiring (payload type lives in amendment text not on hand).

## 2. Architecture options

### Option A — Full native port (Kotlin + Swift) ✅ **chosen (2026-07-29)**

```
┌─────────────────────────────────────────┐
│ Capacitor WebView  (UI: TS/Vue/React)   │
├─────────────────────────────────────────┤
│ Capacitor plugin bridge (JSON events)   │
├──────────────────┬──────────────────────┤
│ Kotlin           │ Swift                │
│  EXI runtime     │  EXI runtime         │
│  generated codec │  generated codec     │
│  XMLDSig         │  XMLDSig             │
│  EVCC FSMs       │  EVCC FSMs           │
│  BC-JCA TLS      │  CryptoKit/BC TLS    │
│                  │  (Ed448: bundled)    │
└──────────────────┴──────────────────────┘
   JSON-LD (WWCP shape) crosses the plugin bridge (§4.4)
```

**Effort:** two emitters (~2,000 LOC each, shared front end) + two runtimes (~800 each) + two
XMLDSig layers + two state-machine ports (~1,100 each) + two TLS/crypto integrations, plus the
generated JSON-LD serializer pass (§4.4). Realistically **5–7 k hand-written LOC per platform**, plus
generated output, plus re-earning the interop knowledge — *but* the vector corpus checks the
codec half for free, which is where most of the byte-sensitivity lives.

**Pros:** smallest binaries, **no runtime to bundle**, cleanest App Store / Play Store story
(matters — this ships to the stores, §8), idiomatic debugging, the Kotlin/TS EXI libraries
are publishable, and — decisively — **no NativeAOT-on-Android risk at all**.

**Cons:** the stack exists three times (C# + Kotlin + Swift); divergence risk on a byte-sensitive
protocol, mitigated by the shared vector oracle; XMLDSig ported twice; and iOS needs a TLS/crypto
answer for the -20 suites (§3.3) — the one genuinely hard part, made tractable by the
controlled-counterpart decision.

### Option B — Shared .NET NativeAOT core (not chosen)

```
┌─────────────────────────────────────────┐
│ Capacitor WebView  (UI: TS/Vue/React)   │
├─────────────────────────────────────────┤
│ Capacitor plugin (TS façade)            │
├──────────────────┬──────────────────────┤
│ Kotlin (JNI)     │ Swift (C-interop)    │
│  thin binding    │  thin binding        │
├──────────────────┴──────────────────────┤
│ libv2gev.so / .a  — NativeAOT           │
│  Vanaheimr.V2G.Exi.*  (unchanged)       │
│  Vanaheimr.V2G.Simulation (EVCC half)   │
│  BouncyCastle managed TLS  ← portable   │
│  + C ABI shim (~400 LOC, new)           │
└─────────────────────────────────────────┘
   OS keystore access injected downward
```

**Effort:** a C ABI shim + event pump (~400 LOC C#), a Kotlin JNI binding (~300), a Swift
binding (~300), a Capacitor plugin (~400 TS), plus build plumbing. **~1.5 k LOC total** versus
~12 k for Option A.

**Pros:** zero re-implementation; all 629 tests keep applying to shipped code; **one** wire
implementation to keep conformant; BouncyCastle solves TLS identically on both platforms;
future -20 amendments land once.

**Cons:** +8–15 MB per platform; NativeAOT-on-Android is the least-trodden path; C# debugging
from a Capacitor app is awkward; BouncyCastle's reflection needs trim/AOT vetting.

*Why not chosen:* its headline win was avoiding the 3× port, but the vector oracle makes the
port low-risk, and its other headline win (managed TLS on iOS) is only decisive when the
counterpart is uncontrolled — which the "real chargers out of scope" decision removes. Weighed
against introducing the Android NativeAOT unknown and a bundled runtime into an app-store build,
the native port is the better trade here. Kept documented as the fallback if the Swift crypto
story (§3.3) turns out worse than expected.

### Option C — TypeScript codec in the WebView

Emit TS from the generator; run codec + XMLDSig in JS; native layer is a dumb TLS pipe.

**Pros:** one language with the UI; trivial hot-reload; and it lands the codec in the same
language as `ChargyCore.TS`, which is where the transparency work ends up.
**Cons:** WebCrypto has P-256/P-521 but **no Ed448**, and no hardware-keystore access, so -20
PnC signing must still cross the bridge. Native TLS problem unchanged. Message volume is tiny
so performance is a non-issue.

**Verdict:** not the app's transport core, but the **TypeScript emitter is the highest-value
third target** — for Chargy, for a browser-based EXI inspector, and as a teaching artefact. It
can also serve as an in-WebView cross-check of the native codecs during development.

### Decision

**Option A (full native port) is the product.** Emitter build order: **Kotlin first** (BouncyCastle
Ed448 is mature there, so it de-risks the crypto path), then **TypeScript** (Chargy + WebView
cross-check), then **Swift** (last, because it carries the one hard crypto gap, §3.3). Option B
stays on file as the fallback should the Swift path prove worse than projected.

**Revised order (2026-07-30): Kotlin → Swift → TypeScript.** Swift and TypeScript swapped places,
for a reason and against a mild cost.

The reason: this machine is the only one in the project with a Swift toolchain — the Windows box
has none — so Swift work is gated on *where the developer is sitting*, in a way TypeScript is not.
And the argument for putting Swift last (the crypto gap) does not survive contact: Ed448 blocks
one of -20's two signature suites and nothing else. P-521 signing, every codec, every fragment and
the whole dispatcher were reachable without it, so deferring the back end would have deferred
89k lines behind an unresolved dependency decision that the back end does not need resolved.

The cost, stated plainly: **TypeScript's cross-check value arrives later than planned.** §4.4
wants three back ends emitting identical JSON-LD, and §2's Option C wants an in-WebView oracle
during development. Two back ends now agree; the third-opinion property is deferred, not
cancelled. In practice the *cross-emitter comparison* (§5, Track A note) turned out to supply the
"independent second opinion" role earlier and more cheaply than a third language would have, which
is why the swap was affordable at all.

## 3. Platform reality check — the risks that actually bite

These are ordered by how likely they are to cost a week you did not plan for.

### 3.1 ✅ ~~NativeAOT for Android~~ — dissolved by the native-port decision

This was the first draft's top risk. The full native port runs **no .NET on the device**, so
the `linux-bionic` RID, the NDK/`libc++` friction and the AOT-trimming of BouncyCastle all fall
away. This is the main reason the native port is the safer bet, not the riskier one. The
residual risk moves to *generated-code size vs. toolchain limits* (§3.7) and the *Swift crypto
gap* (§3.3) — both bounded and known, unlike an unproven runtime port.

### 3.2 🔴 iOS multicast entitlement for SDP

SECC Discovery Protocol is UDP over IPv6 link-local multicast (`ff02::1`). On iOS this requires
`com.apple.developer.networking.multicast`, which needs **explicit Apple approval** and is
routinely declined for non-obvious use cases. Android needs only a `MulticastLock`.

**Mitigation:** treat SDP as **optional from day one.** The primary pairing path is **QR
scanning (§4.5)** — which is not a workaround but the app's central UX concept: the QR stands in
for plug-in + SLAC + SDP together, and carries the endpoint *and* the transport/crypto profile
that SDP's security byte would otherwise announce. Manual IP entry remains as a fallback. Note
the C# EVCC already has a `MulticastLoopback` option and a `FixedSeccDiscovery` seam, so the SDP
path stays available where the platform allows it.

### 3.3 🟠 TLS/crypto on iOS — the one hard part of the native port

ISO 15118-20 + the CharIN TLS implementation guide pin concrete versions, suites and curves
(TLS 1.3, secp521r1, **Ed448** signature schemes, mutual auth). Apple's TLS APIs deliberately do
not expose cipher-suite control, and BoringSSL (swift-nio-ssl) has no Ed448. In a native port
there is no managed BouncyCastle to fall back on.

But the picture is narrower than "iOS can't do -20 TLS", and the **controlled-counterpart
decision** (real chargers out of scope — the only peer is your own Pi, §8) is what makes it
tractable. Break it into the two -20 signature suites:

| -20 crypto suite | Kotlin/Android | iOS |
|---|---|---|
| **ECDSA secp521r1 / SHA-512** | JCA + Conscrypt, or BouncyCastle | ✅ **CryptoKit has P-521** natively |
| **Ed448** | ✅ BouncyCastle-Java | ❌ not in CryptoKit; needs bundled BC-Swift / OpenSSL / wolfSSL |

So the honest position for the port:

1. **App-layer XMLDSig** (PnC signatures, signed metering) is *not* TLS and does not need Apple's
   TLS stack. On iOS, CryptoKit signs/verifies the **P-521 suite** natively; only **Ed448**
   needs a bundled crypto lib. Kotlin does both via BouncyCastle. → the signing features work on
   both platforms today, with Ed448 the sole iOS extra.
2. **Transport TLS** is the real constraint, and because **both endpoints are yours**, you pick
   the suite. Design two modes explicitly:
   - **Conformant mode** — the full CharIN -20 profile (secp521r1, Ed448-capable), via a bundled
     TLS lib on iOS. This is what exercises the real protocol and what the Scorecard (§7.1) needs.
   - **Relaxed/interop mode** — a mutually-supported platform-friendly suite (TLS 1.3 + P-256,
     or plaintext TCP), so the app runs on stock iOS TLS with no bundled crypto. Perfectly fine
     for an educational/debugging tool whose peer is a Pi you configure to match.
   The Pi (`BcV2GTlsServer`) can already offer either, so the app chooses; the UI must **state
   which mode is active** so nobody mistakes relaxed-mode for a conformance result.

**How the mode gets selected: the pairing QR declares it (§4.5).** Rather than a build flag or a
guess, the counterpart announces its profile in the scanned payload — `crypto=secp256r1`,
`nc=1`, plus a free-text reason the app displays verbatim. So a relaxed session is relaxed
*because the peer asked for it, on the record*, and the deviation is visible in the UI and in the
session artefacts rather than buried in configuration.

**Net:** ship v1 in relaxed mode + native CryptoKit/BC app-layer signing (no bundled TLS on
iOS), and add a bundled TLS lib for conformant mode as a defined follow-up. This keeps the one
genuinely hard dependency off the critical path to a working app.

#### Measured, 2026-07-30 — point 1 is done; point 2 is untouched

The app-layer half of this section is no longer a projection. Both back ends sign and verify:

| | Kotlin | Swift |
|---|---|---|
| -2, ECDSA P-256 / SHA-256, raw `r‖s`, 64 B | ✅ | ✅ CryptoKit `rawRepresentation` |
| -20, ECDSA P-521 / SHA-512, raw `r‖s`, 132 B | ✅ | ✅ CryptoKit, natively |
| -20, Ed448, 114 B | ✅ BouncyCastle | ✅ `V2GEd448` over vendored libgoldilocks, vector-checked against RFC 8032 §7.4 |

That last cell was the hard one, and the plan understated it: this is **not** an
unregistered-provider problem of the kind the JVM has, where BouncyCastle supplies what the JDK
omits — the primitive does not exist in Apple's library, so there is nothing to register. It was a
bundled-dependency decision or nothing.

**Closed 2026-07-30** by bundling libgoldilocks (§8 #10 for what decided it), so the app-layer
half of this section is now complete on both platforms. Pure Ed448, empty context, 114 bytes,
matching `#eddsa-ed448`; the prehashed `#eddsa-ed448ph` is a different algorithm and is refused by
name rather than silently signed as if it were the pure one.

Worth keeping from the interim state, because it outlived the gap that prompted it: every entry
point now dispatches on the algorithm the `SignedInfo` **declares**, not on the signature's length.
A caller must be able to distinguish *unsupported algorithm* from *invalid signature* — the first
is a reason to renegotiate, the second a reason to reject the peer — and a length was a guess at
something the message had already told us.

**Point 2, transport TLS on iOS, has not been touched at all** and is still exactly as written
above: relaxed mode for v1, bundled lib for conformant mode. Nothing in the port makes it easier
or harder than projected.

#### A related finding from the host side: .NET on macOS has no TLS 1.3 either

Discovered while setting this machine up, and worth recording here because it is the same *shape*
of problem one layer down. `SslStream` on macOS runs on Apple's deprecated SecureTransport, which
has no TLS 1.3 — so a TLS-1.3-only `SslProtocols` throws `PlatformNotSupportedException`, and the
C# -20 tests could not run on a Mac at all.

Two things about the fix generalise to §3.3's iOS problem:

- **The obvious repair was the wrong one.** Widening to `Tls12 | Tls13` makes the tests pass; it
  was *measured* to negotiate TLS 1.2, which would silently drop -20 below its mandated version.
  A green suite would then have been evidence of nothing. The protocol set is now `required` with
  no default, because a single default cannot serve both -2 (TLS 1.2) and -20 (TLS 1.3).
- **The working repair was a platform fallback**, routing TLS-1.3-only sessions through the
  managed BouncyCastle stack on macOS only — which is structurally the same answer §3.3 proposes
  for iOS conformant mode, now with one instance of it built and passing.

Cipher-suite pinning came with the same lesson in reverse: `CipherSuitesPolicy` is unsupported on
Windows/Schannel and throws in its *constructor*, so the pin cannot be enforced on either of this
project's two machines — macOS pins via BouncyCastle, Windows cannot pin at all, and only Linux
enforces per connection. The pin was kept anyway for its stated intent and its deviation log.
Details in `Vanaheimr.V2G.Exi/docs/pki-model.md`.

### 3.4 🟠 Hardware-backed keys don't cover -20

| Store | Curves | -2 contract cert (P-256) | -20 contract cert (P-521 / Ed448) |
|---|---|---|---|
| iOS Secure Enclave | P-256 only | ✅ | ❌ |
| Android StrongBox / TEE | P-256, RSA (varies) | ✅ (device-dependent) | ❌ |

So: **-2 PnC keys can be Secure-Enclave-backed; -20 keys cannot.** -20 private keys must live
as software keys in Keychain / EncryptedSharedPreferences, ideally with biometric gating on
*use* rather than on storage. Design the key store around this asymmetry from the start rather
than discovering it at the first P-521 keygen. Be explicit about it in the UI — a simulator
that quietly pretends its keys are hardware-protected is worse than one that says they aren't.

Note this hardware/software split is **orthogonal** to the CryptoKit/BC software-crypto split in
§3.3: CryptoKit can *operate on* a software P-521 key held in the Keychain; the Secure Enclave
limitation is only about which keys get *hardware* protection. Software P-521/Ed448 keys are fine
functionally — they just aren't enclave-bound, which for a simulator is acceptable if disclosed.

### 3.5 🟠 iOS background execution

Charging sessions run for hours; the -20 ChargeLoop is a continuous exchange. iOS suspends
apps. Even with background modes, a socket-holding app is on borrowed time.

**Mitigation:** design the session engine to survive suspension — persistent session state,
explicit `Pause`/`Resume` ([V2G2-740]) on backgrounding, and reconnect-with-resume rather than
"keep the socket alive and hope". This is *also* a genuine protocol feature worth exercising,
so the constraint and the feature align nicely.

### 3.6 🟡 No PLC / SLAC on a phone

Accepted and explicitly out of scope — WLAN replaces PLC. Two honest consequences:

- The link-layer half of 15118 (SLAC, HomePlug Green PHY, -3 signalling, Control Pilot states)
  is **not** exercised. The app tests everything from IP upward.
- The RPi SECC must accept a TCP connection arriving over WLAN rather than the PLC interface.
  `TcpV2GListener` already does this; only interface binding needs attention.

This is exactly the same slice ISO 15118-**8** defines (802.11 as the wireless PHY/DLL, no EXI
changes) — so the setup is closer to a real profile than it may look. Worth saying in the app's
own docs: this is a -8-shaped deployment, not a hack.

Note this is a **phone** limitation, not a stack limitation: `WWCP_ISO15118_SLAC` has a real
`QcaChipController` and AF_PACKET transport, so the *Pi side* can speak genuine PLC SLAC to
real hardware whenever a Green PHY modem is attached — and can also run the `SLACBridge` for
MitM research. The phone simply enters the story one layer up, at the TCP/TLS socket over WLAN.
So the interesting SLAC-layer experiments (§7.1's lower-layer probes) live on the Pi, driven
*from* the app, rather than on the phone itself.

### 3.7 🟠 Generated-code size vs. toolchain limits (now on the critical path)

With the native port chosen, this is no longer a side-project concern. The -20 AC codec is 15k
LOC in one file; AC_DER_SAE is 34k. In Kotlin this approaches DEX method limits and slow builds;
in Swift, single files of that size are a well-known type-checker performance cliff. **The
Kotlin and Swift emitters must split output per type**, unlike the C# emitter which happily
emits one file per schema. Design the emitter around per-type files from the start (Phase 1),
not afterwards.

**Confirmed and handled (2026-07-30).** Both back ends split per type from their first commit, and
the resulting shape is what the warning predicted: Swift's 89,670 lines land in **669 files**, the
largest set (`AC_DER_SAE`, 25,788 lines) in 108 of them. `SwiftEmitterSplitTests` asserts the
split structurally — one file per type, nothing declared twice — so a regression cannot arrive
quietly as a slow build.

Because the splitting was designed in rather than retrofitted, the type-checker cliff was never
hit and there is **no measurement of where it would have been**. That is the good outcome, but it
means the risk is avoided rather than quantified: if the emitter is ever tempted back toward
larger files, this section is a prediction again, not a result.

## 4. Feature design

### 4.1 Certificate management (GUI)

Five certificate roles, per `docs/pki-model.md` and the CharIN V2G 2nd-gen CP:

| Role | Held | Used for | Private key on device? |
|---|---|---|---|
| **Vehicle certificate** | EV | TLS 1.3 client auth (-20 mutual TLS) | ✅ |
| **Contract certificate** (1…n) | EV | PnC signing (`AuthorizationReq`, metering) | ✅ |
| **OEM Provisioning certificate** | EV | `CertificateInstallation` bootstrap | ✅ |
| **V2G Root CA** (1…n) | EV | verify SECC leaf chain | — |
| **MO Root CA** | EV | verify signed tariffs / provisioning | — |

**UI model — a "Vehicle Wallet" tab:**

- **Import**: PKCS#12 (`.p12`), PEM bundle, DER. Via file picker, QR (for small material),
  clipboard, or pull from a local dev PKI service on the RPi.
- **Generate on device**: keypair in Keychain/Keystore → CSR export → sign externally →
  re-import the leaf. This is the realistic OEM flow and it is the only one that keeps the
  private key from ever existing off-device.
- **Inspect**: subject/issuer, validity, curve, SKI/AKI, chain resolution status, trust-anchor
  match, and the **domain-component checks** the CharIN TLS guide requires on SECC certs.
- **Multiple contracts**: hold ≥2 with different providers — the interesting case, because
  `AuthorizationSetupRes` advertises accepted providers and the EVCC must *select*. The C#
  stack already models this; the GUI should make the selection visible and overridable.
- **Deliberate breakage**: expired cert, wrong root, wrong curve, revoked cert — one tap each.
  For a simulator this is a feature, not an edge case (see §6.3).
- **Test PKI generator**: `WWCP_ISO15118_PKI` (now a submodule) builds the full hierarchy with
  `strict-2` (P-256) and `strict-20` (P-521/Ed448) profiles. Expose it as "generate a complete
  test PKI" so a new user has a working wallet in one tap. Ship it as an RPi-side service, not
  on the phone.
- **Evil-certificate library**: `WWCP_ISO15118_PKI/Evil/` already ships ~14 deliberately broken
  certs (`evil_twin_root`, `path_len_violation`, `secc_wildcard_san`, weak RSA, `ku_not_critical`,
  …). The wallet's "deliberate breakage" toggles below should be *backed by this factory*, not
  reinvented — and the same set is the ammunition for the Security Scorecard (§7.1).

**Storage:** certificates in app storage; **private keys never leave the platform keystore**,
with the §3.4 caveat surfaced in the UI per key.

### 4.2 EV-signed meter readings

The "rarely used feature" is genuine, standardised, and **already implemented in the C# stack**
(the roadmap lists signed `MeteringReceiptReq` as live against Josev). Two forms:

**ISO 15118-2 — `MeteringReceiptReq`**
The SECC sets `ReceiptRequired` in `ChargingStatusRes` / `CurrentDemandRes`. The EVCC replies
with a `MeteringReceiptReq` carrying the SECC's `MeterInfo`, signed with the **contract
certificate private key** via XMLDSig over the EXI fragment. Semantically: *the EV
countersigns the station's meter reading.*

**ISO 15118-20 — `MeteringConfirmationReq` + `SignedMeteringDataType`**
The -20 successor. `SignedMeteringDataType` carries `SessionID`, `MeterInfo`, optional
`Receipt`, and a control-mode branch — and crucially has `Id` as `xs:ID`, i.e. it is a
*signable fragment* referenced from the message header `Signature`. Same idea, richer payload,
stronger suites (P-521/SHA-512 or Ed448).

**What the app should add on top:**
- Show the exact bytes being signed (the canonical EXI fragment), the digest, and the
  signature — this is the part nobody can normally see, and it is the whole point of a
  simulator.
- Independent local meter model in the EV (see §4.3) so the signature covers *the EV's own
  view*, not only an echo of the station's.
- Persist every signed receipt as a session artefact, exportable.

### 4.3 The Chargy endgame — better than a vendor extension

The plan was: "later, via VendorExtensions, send signed meter readings to the simulated EV and
compare EV vs station measurements". Two corrections that make this *easier*:

**1. The standard already carries a signed station meter reading — no extension needed.**

```
ISO 15118-2   MeterInfoType.SigMeterReading   xs:base64Binary, maxLength 64
ISO 15118-20  MeterInfoType.MeterSignature    xs:base64Binary, maxLength 64
```

64 bytes is exactly a raw ECDSA P-256 `r||s` signature. These fields exist so the **meter**
(not the SECC, not the CPO backend) can sign its own reading and hand it to the vehicle. That
is precisely the Chargy/Eichrecht trust model, transported over stock ISO 15118, and it is
almost never populated in the field. Having a phone that *displays and verifies* it would be
novel on its own.

**2. What genuinely needs a carrier is the transparency record, not the signature.**

64 bytes carries the signature but not the meter public key, meter serial, OCMF envelope,
tariff, or adapter ID. That needs a side channel. Best carrier, in order:

- **A custom -20 VAS.** `ServiceDiscoveryRes.VASList` advertises value-added services; the EV
  selects one and `ServiceDetail` returns a `ServiceParameterList` of name/value pairs. A
  private service ID = a clean, in-band, schema-valid channel. This is what VAS is *for*, and
  it beats an ad-hoc vendor blob.
- **The -20 Internet VAS** for bulk. EVerest already ships `Iso15118InternetVas`; once
  negotiated, push OCMF/Chargy JSON over plain HTTP inside the session. Right answer for
  anything larger than a few hundred bytes.
- **-2:** no generic vendor extension exists; `ServiceDetail`'s `ParameterSet` (255 max) is the
  only comparable seam, and it is cramped. **Do Chargy on -20 first.**

**The three-way comparison is the real prize.** You already own a CSMS. The full picture:

```
        EV meter model   ──┐
   SECC signed MeterInfo ──┼──►  Chargy verification  ──►  agreement / deviation report
      OCPP MeterValues   ──┘         (in-app)
```

Three independent measurements of the same energy, two of them cryptographically signed by
different parties, verified on a phone. That is a demo nobody has, and it is a *regulatory*
argument (Eichrecht transparency at the point of consumption), not just a technical one.

### 4.4 Object model & the JSON-LD bridge (decided 2026-07-29)

**Decision: the source generator emits the JSON-LD (de)serializer as a second pass, generated
from the XSD model — and the existing hand-written `WWCP_ISO15118_20` JSON-LD code is *not*
reused.**

The first draft of this section proposed reconciling the generated records with WWCP's
hand-written -20 model and using the latter as a JSON oracle. Dropped, deliberately: the
reconciliation was the single most expensive and least mechanical piece of work in the plan, and
it existed only to preserve code the generator can produce anyway.

What the generated approach buys:

- **One model, one source of truth.** Wire codec and JSON-LD codec come from the *same* type
  graph in the *same* generator pass, so they cannot drift — the failure mode a hand-written
  mapper alongside a generated codec guarantees over time.
- **-2 and -20 are treated identically.** This is the big win. `WWCP_ISO15118_2` is empty, so the
  reconciliation plan needed a whole preliminary workstream (design a -2 model by hand, *then*
  map it). Generating removes that workstream entirely — -2 falls out of the same machinery,
  including the structurally awkward `V2G_Message` wrapper and substitution-group body.
- **Three languages for free.** Kotlin, TypeScript and Swift each get a JSON-LD serializer from
  the same pass. A hand-written mapper would have to be written three times and kept in sync.
- **Schema updates stay cheap.** A future -20 amendment regenerates both codecs; nothing to
  hand-maintain.

Design notes:

- **Naming rules are emitter configuration**, derived mechanically from the XSD names. WWCP's
  conventions (no `Req`/`Res` suffixes, plural collection names, `@context`) remain useful as
  *style guidance* for that rule table — the good ideas are worth keeping even though the code
  isn't.
- **`@context` per namespace**, matching the JSON-LD flavour and keeping -2 and -20 messages
  self-describing on the bridge.
- **The generated records stay the runtime wire type** — they own byte-exactness, which is never
  compromised for JSON convenience.

**The honest cost: this gives up an oracle.** The bytes keep theirs (libcbv2g vectors); the JSON
now has none, because the thing that would have checked it is the code being set aside. Two
cheap compensations, and they should be built in from the start rather than retrofitted:

1. **Round-trip property tests** — `decode(EXI) → JSON → parse → encode(EXI)` must reproduce the
   original bytes, over the whole existing vector corpus. That catches any lossy or wrong
   mapping without needing a second implementation.
2. **Cross-language agreement** — Kotlin, TypeScript and Swift must emit *identical* JSON for the
   same input. Three independent emitter backends agreeing is a real (if internal) check, and it
   is exactly the property the app needs anyway.

Optionally, spot-diffing a handful of -20 messages against `WWCP.ToJSON` remains available as a
sanity check on the naming rules — using the old model as a *reference reading*, not as a
dependency.

### 4.5 QR pairing — the "virtual plug" and out-of-band pre-negotiation

**Decision (2026-07-29): a QR scanner is a core feature, and the QR payload carries metadata,
not just an endpoint.**

The framing is the valuable part: **the QR code stands in for the entire physical-layer
bootstrap.** Look at what it replaces, one for one:

| Real CCS | What it establishes | QR equivalent |
|---|---|---|
| Plug in the cable | *This EV is attached to that EVSE* | A **dynamic TOTP** code on the EVSE's display — you must be physically there **now** (§4.6) |
| SLAC | Pair over the right PLC link, pick the nearest EVSE by attenuation | The code you scan **is** the choice — no ambiguity to resolve |
| SDP multicast | Discover SECC IP, port, and the **security byte** (TLS / no-TLS) | Endpoint + transport + crypto profile, carried in the payload |

That third row is the key insight and it is what makes the metadata idea principled rather than
a hack: **SDP's response already carries a security byte** — a one-byte "TLS or plaintext"
declaration. Putting a *richer* crypto profile in the QR is the honest generalisation of a field
the protocol already has, moved to an out-of-band channel because the in-band one (multicast) is
unavailable on iOS anyway (§3.2). It also lands the app on the ISO 15118-**8** side of the
family, where discovery is likewise not PLC-shaped.

**And it directly resolves the -20 TLS problem (§3.3).** Instead of the app guessing or a
build-time flag, the counterpart *declares* its profile: "for -20, use secp256r1 — for
reasons™". The reason string is carried too, and the app **displays it**, which turns a quiet
non-conformance into a visible, attributed one. That closes the open UX question (§8.9).

#### Payload format

An **HTTPS universal link with the data in the fragment**:

```
https://open.charging.cloud/evsim/pair#v=1&host=fe80::1%25wlan0&port=15118&…
```

Two deliberate properties:

- **Fragments are never sent to a server.** A code scanned with the stock camera app opens a
  harmless landing page (useful: it can explain what the app is), while the endpoint, profile and
  fingerprints stay client-side. A custom scheme (`v2gsim://`) is supported as an alias for
  in-app scanning, but the HTTPS form is what goes on a sticker.
- **Deep-links straight into the pairing sheet** on both platforms.

**Do not invent a parallel vocabulary.** `DynamicQRCodes`' `ProcessURLTemplate` already defines
the OCPP v2.1 / AFIR template parameters, and several of them are exactly what this app needs.
Reuse those names and **add only the V2G-transport-specific ones**, so the app's pairing code is a
*superset* of a conformant AFIR QR — and a real AFIR charger's code partially works in the app.

Existing OCPP v2.1 parameters (from the library):

| Field | Purpose here |
|---|---|
| `{totp}` | **the dynamic freshness proof** (§4.6) — what changes every slot |
| `{version}` | payload/template version |
| `{evseId}`, `{connectorId}`, `{evRoamingEVSEId}` | identify the EVSE (e.g. `DE*GEF*E12345678*1`) — UX and session context |
| `{maxEnergy}`, `{maxTime}`, `{maxSoC}`, `{endTime}` | session intent — maps onto EV charge-parameter limits and departure time |
| `{tariffId}`, `{maxCost}`, `{currency}` | pricing context — feeds the signed-tariff features (§6.2) and the tariff view (§7.6) |
| `{chargingProfile}`, `{chargingSpeed}` | preset scenario — replaces the `mode` field I had invented |
| `{uiLanguage}` | UI language |

New, V2G-specific additions:

| Field | Purpose |
|---|---|
| `host`, `port` | SECC endpoint — IPv6 (incl. link-local + zone), IPv4, or mDNS name |
| `tp` | transport: `tcp` \| `tls` — the SDP security byte's job |
| `proto` | offered protocols, e.g. `iso2,iso20` (+ preference). A *hint*; SAP still runs for real |
| **`crypto`** | **the point of this exercise** — e.g. `secp256r1` for -20 instead of secp521r1/Ed448 |
| **`nc`, `ncwhy`** | non-conformance flag + human-readable reason, **displayed verbatim** by the app |
| `root` | SHA-256 fingerprint of the V2G Root CA → **trust bootstrap without a pre-seeded store** |
| `meter` | meter public key / id — enables Chargy verification (§4.3) from first contact |
| `wifi` | optional SSID + PSK, if the Pi runs its own AP (see below) |
| `sig` | optional signature over the payload (see security) |

That the OCPP vocabulary already carries `{tariffId}`, `{maxCost}` and `{currency}` is a small
windfall: the pairing step can hand the EV its **pricing context before the session starts**,
which is exactly the input the signed-tariff verification and the cheapest-window view want.

`root` deserves emphasis: it lets a freshly installed app validate the Pi's chain **without any
manual trust configuration** — scan, pin, connect. That is a real bootstrap problem solved, not
just convenience.

**WLAN join in the same scan.** If the Pi runs its own access point, `wifi` makes
scan → join → connect a single action — the closest thing to "plugging in" that a phone can do.
Feasible on both platforms (`NEHotspotConfiguration` on iOS, `WifiNetworkSuggestion` on Android),
and it removes the most annoying part of a demo setup.

#### Security — a QR code is untrusted input

This must be stated plainly, because the feature's whole job is to configure security parameters
from a scanned image, and malicious-sticker attacks ("quishing") are an established problem at
public chargers specifically.

**A dynamic (TOTP) code is itself a large part of the answer** — that is the AFIR motivation
behind the OCPP v2.1 mechanism (§4.6). A printed sticker, once photographed, replays forever; a
displayed TOTP code is only valid for its slot, so a stolen image is worthless within ~30 s and
the *attacker* has to be present too. It does not stop someone taping a fake display over a real
one, so the rest of these still apply:

- **Never auto-execute.** Scanning opens a **confirmation sheet** showing endpoint, protocol,
  crypto profile and any non-conformance reason. Connecting is an explicit tap.
- **Downgrades are loud.** `tp=tcp` or a weakened `crypto` renders as a prominent warning, never
  as a quiet default — consistent with the §3.3 rule that relaxed mode must never be mistaken for
  a conformance result.
- **Restrict targets by default** to private / link-local ranges. The intended counterpart is a Pi
  on your own network; a QR pointing at a public host is suspicious by construction and should
  require an explicit override (and is out of scope anyway, §8).
- **Certificates and private keys are never transmitted** because of a scan. The QR may carry a
  *public* fingerprint (`root`, `meter`); it can never carry or request key material, and it must
  not be able to select which contract certificate is used for signing without confirmation.
- **Optional payload signature** (`sig`): if the app already trusts a root, it can verify the QR
  itself, giving authenticated pairing. Nice-to-have, not v1.

The generator side belongs to the Pi (§5, B0): it knows its own endpoint, profile and
fingerprints, so it should render its current pairing QR on a status page — self-describing and
always in sync with its actual configuration.

### 4.6 Dynamic TOTP QR codes — a real SLAC substitute

**Reuse `OpenChargingCloud/DynamicQRCodes`** — the reference implementation of the dynamic-QR
mechanism written for EU AFIR and adopted into **OCPP v2.1** (visible to OCA members since Draft3
v0.53). The Pi displays a QR code that changes every few seconds; the app scans it; the Pi can
*independently verify* what the app presents.

This upgrades §4.5 from a UX convenience to a **security property**, and it fixes the weakest
claim in that section. "You must be physically there to scan" is nearly worthless for a static
sticker — photograph it once and replay forever. With a rotating code the claim becomes:

> The EV proves it had **visual line-of-sight to this EVSE's display within the last slot
> (~30 s)**, and the SECC can verify that proof on its own.

That is a **proximity proof**, and proximity is precisely what SLAC provides in real CCS —
SLAC's actual security content is "these two endpoints share a physical medium". Different
medium, same class of guarantee, and considerably easier to reason about than signal attenuation.
So the QR does not merely *replace* SLAC's UX; it substitutes for its security role too.

#### The algorithm (as implemented)

From `TOTP/CSharp/TOTPSharp/TOTP.cs` — RFC 6238-shaped, with deliberate deviations:

- `slot = unixTime / validityTime` (default **30 s**), HMAC-SHA256 over the **big-endian** slot.
- RFC 4226-style dynamic offset: `offset = hash[^1] & 0x0F`, then characters selected from an
  alphabet — default **base62**, default length **12** (≈71 bits, far beyond RFC 6238's 6–8
  digits, because this is not typed by a human).
- Returns **previous / current / next** plus `RemainingTime` → **±1 slot of clock-skew
  tolerance** is built in, which matters here because a phone's clock is not trustworthy.
- Shared secret ≥ 16 chars.

The library also ships **`GenerateURL` / `GenerateURLs`**, which apply the TOTP to a URL template
via `ProcessURLTemplate` — i.e. the QR *URL* construction is already solved, along with the OCPP
v2.1 parameter vocabulary reused in §4.5. `GenerateURLs` returns previous/current/next URLs plus
`RemainingTime` **and `EndTime`**, so the Pi's display page gets its refresh schedule for free and
the app can show an accurate countdown.

Reference implementations already exist in C# and JavaScript, plus an Android app — so the Pi
side is essentially free, and the **TypeScript emitter target (§2, Option C) lines up with the
existing JS implementation** for the app side.

Added as `libs/DynamicQRCodes` (2026-07-29), pinned at `6ef62a5`.

#### Carrying the TOTP into the V2G session

Your instinct — send it during session setup so the Pi can *additionally* verify — is right, and
there is a principled place for it. Three tiers, best first:

**Tier 1 (recommended): verify in the pairing step, before the V2G session.**
The structural argument: **SLAC is not part of the V2G message set either.** It runs first,
outside the session, and gates everything that follows. A TOTP check that gates the TCP accept
sits in *exactly* the same architectural slot — and since the QR has already replaced SDP, this
is simply the SDP-replacement handshake doing what SDP's security byte hinted at. Properties:
protocol-agnostic (works identically for -2 and -20), **zero schema deviation**, and the SECC can
refuse the connection outright rather than aborting a half-built session.

**Tier 2 (optional, -20 only): echo it in `SessionSetupReq.EVCCID`.**
Confirmed from the schema: -20's `EVCCID` is `identifierType` = `xs:string`, **maxLength 255** —
ample room for a 12-character TOTP, in the **first** EVCC→SECC application message. This makes
the proof visible *inside* the session, so it lands in the session artefacts and the protocol
inspector rather than only in a pre-flight log. Worth doing as a demo of in-band presence proof —
but flag it honestly as a **deliberate deviation**: `EVCCID` is meant to identify the vehicle
controller (conventionally MAC-derived), not to carry a session credential. Structured, e.g.
`<evccid>+totp=<totp>`, so a plain EVCCID still parses.

**Tier 3 (fallback, protocol-agnostic): TLS-layer binding**, e.g. the TOTP as the SNI value. No
15118 impact at all, works for -2 and -20, but obscure — only worth it if Tier 1's handshake is
unwanted.

**Honest limitation for ISO 15118-2.** There is *no* in-band room:

| | -2 | -20 |
|---|---|---|
| `EVCCID` | `evccIDType` = `xs:hexBinary`, **maxLength 6** (a MAC) | `identifierType` = `xs:string`, maxLength 255 ✅ |
| EIM authorization payload | none | `EIM_AReqAuthorizationModeType` is an **empty complexType** — literally nothing |
| Other EVCC→SECC free fields | `ParameterSetID` (`xs:short`, 16 bits) | ditto |

So -2 relies on the Tier-1 check only. That asymmetry is worth stating rather than papering over,
and it is a small argument for doing Tier 1 properly instead of treating Tier 2 as the mechanism.

#### Security notes

- **Secret provisioning is the chicken-and-egg.** The Pi and app must share a secret before the
  first dynamic code means anything. For a simulator, carry it once in an initial *static* setup
  QR (alongside `root`), or via the test-PKI bootstrap — and never in the rotating code itself.
- **Never put the shared secret in the displayed QR** — only the derived `totp`.
- **Replay inside the slot is possible.** Bound it: the SECC should accept each TOTP **once**
  (nonce cache over the accepted slots), which turns the ±1-slot skew window from a replay
  window into a one-shot credential.
- **Do not trust the phone's clock.** The prev/current/next construction already tolerates ±1
  slot; the app should send what it read, not what it thinks the time is.
- **Bind the proof to the session** if it matters: including the TOTP in the session artefacts
  (Tier 2, or the pairing log) makes "this session began with a verified proximity proof" an
  auditable statement rather than a transient check.

#### Why this is more than a nice trick

Two follow-on possibilities worth recording:

- **Same secret, three protocols.** If the CSMS shares the TOTP secret, the *same* proximity
  proof can appear in OCPP (`Authorize` / `TransactionEvent`) and in the 15118 session — tying
  the AFIR payment story to the charging session cryptographically. That connects directly to the
  three-way meter comparison (§4.3) and your existing CSMS.
- **A conformance/education artefact.** "Proximity proof" is exactly the property most people
  cannot articulate about SLAC. An app that demonstrates SLAC's guarantee *without PLC*, and
  shows the verification succeeding and failing (expired slot, wrong secret, replayed code), is a
  genuinely good teaching device — and slots straight into the teaching mode (§7.8) and the
  negative-test catalogue (§6.3).

## 5. Work plan

Effort assumes one experienced developer, part-time. With the **full native port** chosen, the
plan has two tracks that meet at the app:

- **Track A — the native 15118 stack** (the port itself): generator retarget → Kotlin, then
  TypeScript, then Swift codecs, each with runtime, XMLDSig, state machines and the JSON-LD
  serializer (§4.4). This is now the critical path, not a side project.

The plan feared "the dual-grammar signature story (cbV2G-combined + Josev-standalone)" and

It will still have to be re-earned in **A4**, where it actually lives.

sets.** Each -20 set embeds its own copy of the XMLDSig schema and sizes the fragment selector over
the whole set, so the same `SignedInfo` lands on event code 230/9 bits under CommonMessages, 135/8
under AC and 129/8 under DC. One shared helper would sign octets no peer asked for — a signature
that verifies locally and nowhere else. Hence five near-identical copies in each back end, which
looks like duplication and is not.

#### Track A note: the gate that was documented but did not exist

The most useful finding of the Swift port is about *checking*, not about Swift.

`kotlin/README.md` describes three independent gates on generated code: (1) the libcbv2g vector
corpus, (2) a **cross-emitter comparison** reducing each back end's output to its ordered wire
operations and requiring the back ends to agree, (3) structural tests. Gate 2 was described as
standing. It had **no implementation in the repository** — the Kotlin-era comparison had been an
ad-hoc run whose tool was never checked in, so nothing would have caught a regression in it.

It was built during the Swift port (`CrossEmitterComparisonTests`) and immediately earned its
place. It compares each back end against C# across every whole schema set it generates — seven for
Swift, and since 2026-07-30 **eight for Kotlin**, the extra one being WPT, which only Kotlin
emits. It found **four real bugs that vectors, compilation and round-trips all missed**, of which
two make the argument by themselves:

- `SalesTariffEntryType` wrote a **1-bit run selector where cbV2G writes 2**, because an optional
  *list* was treated as terminating an optional run rather than belonging to it. Every bit after
  that selector was wrong. The codec compiled and round-tripped against itself perfectly.
- An `xs:choice` **decoder never read the element End Element its encoder writes**, so a real
  stream would have desynchronised by one bit after every choice. This one is the *other* blind
  spot: encoder and decoder disagreed, and a round trip would have caught it — if any vector had
  exercised that construct. None does. So the two gaps compound: vectors miss what both halves get
  wrong together, and they equally miss what no vector happens to cover.

The general lesson, and it applies well beyond this port: **a vector corpus pins the encoder, and
the decoder is then checked by round-tripping through that same encoder.** A bug mirrored in both
directions passes every gate that only compares a codec to itself. §0 calls the corpus "a free
byte-exact oracle" — true, and it is not sufficient on its own.

The second-order lesson matches the one Phase 1 already recorded about the "language-neutral"
front end: **a documented check is not a running check.** Both times, something this document
counted as an asset turned out to need building before it could be counted.

**Extending it to Kotlin (2026-07-30) produced a third instance of the same lesson**, one layer up.
Kotlin needed no emitter change — the one divergence was the document-index switch, which Kotlin
writes in plan order and C# and Swift write sorted by index. The same table, and a keyed switch's
arm order is not wire structure, so the comparison was wrong, not the emitter.

Fixing that exposed the real gap: to sort arms the comparison has to *see* the keys, and it had
never been looking at them. Every back end could have routed document index 4 to the wrong message
and passed — the operation sequences would have matched, since only the calls beneath the arms were
compared. The vectors would not have caught it either: a misrouted document decodes into a
well-formed instance of the wrong type and re-encodes to the bytes it came from, because both
directions consult the same table. That mapping is now checked directly, per set, across all three
back ends. Nothing was broken; the point is that nothing would have said so.

## 6. ISO 15118 features you may have missed

A checklist, roughly by "how often it is forgotten". ✅ = already in the C# stack.

### 6.1 Commonly skipped, genuinely important

| Feature | Notes |
|---|---|
| **DIN SPEC 70121 fallback** | ⬜ **Parked by decision — kept on the optional to-do list.** Many deployed DC chargers speak *only* DIN 70121; libcbv2g covers it and `WWCP_DINSpec` is a ready (empty) home for it, but it is out of scope for now. | **CRL / OCSP checking** | -20 §7.9.2 expects revocation handling on contract certs. Almost universally skipped. A simulator that *does* check is a good differentiator. |
| **`CertificateUpdate` / expiry-triggered renewal** | The EV must notice a contract cert nearing expiry and renew. The trigger logic is what's usually missing, not the message. |
| **`DisplayParameters` (-20)** | The EV telling the charger SOC / remaining time / target so the charger's own display is correct. Trivially implementable, very visible in a demo. |
| **`EVSEProcessing = Ongoing` + EIM polling** | The EIM authorization loop with real timeouts. Easy to fake, easy to get wrong. |
| **Timeout budgets** | `V2G_SECC_Sequence_Timeout`, `V2G_EVCC_Msg_Timeout`, performance timing. ✅ modelled (`MessageTimeoutOptions`) — but the app should *visualise* them (Phase 6). |
| **TLS session resumption** | -20 permits it to speed up reconnect after pause. Directly relevant to §3.5's iOS suspension design. |
| **SECC cert domain-component checks** | The CharIN TLS guide's rules; a common source of field failures. |
| **Short-lived SECC leaf certificates** | ~30-day validity in the CP; clock-skew failures are a classic. |

### 6.3 Negative testing — the part simulators forget

A simulator's most valuable mode is the one that misbehaves. All cheap given the architecture,
and now largely *pre-supplied* by `WWCP_ISO15118` rather than needing to be hand-built:

- Wrong/expired/revoked certificates; wrong root; wrong curve — ✅ `PKI/Evil/` factory.
- **TOTP pairing failures (§4.6)**: expired slot, replayed code, wrong shared secret, skewed
  clock at ±1 and ±2 slots, a screenshot of an old code. Cheap, and they demonstrate the
  proximity property better than any explanation.
- SLAC-layer attacks (spoofing, MitM, the CVE-2025-12357 class) — ✅ `WWCP_ISO15118_SLAC`'s
  `SLACBridge`, Pi-side (see §3.6).
- Malformed EXI, truncated V2GTP frames, wrong payload type, wrong protocol version.
- Timeout violations in both directions; late responses; message-out-of-sequence.
- Invalid signatures; replayed `GenChallenge`; tampered `MeterInfo` (does the SECC notice?).
- TLS downgrade attempts; missing client cert; unexpected renegotiation.
- Abrupt disconnect mid-`ChargeLoop`; resume with a stale SessionID.

## 7. Ideas nobody has built yet

Ordered by "cool per unit of effort", given that Phase 6's event stream makes most of them
nearly free.

**1. 🏆 Charger Security Scorecard.**
Point the app at any charger and get a report card: TLS version accepted, downgrade to 1.2?,
client cert actually verified or waved through?, curve strength, certificate chain validity,
revocation checked?, does it accept a tampered `MeterInfo`?, does it verify PnC signatures at
all? This is SSL Labs for charging infrastructure. It does not exist, it is directly useful,
it is publishable — and with `WWCP_ISO15118` in the tree it is now **mostly assembly rather
than invention**: the `Evil/` certificate factory supplies the client-cert probes (does the
SECC reject `evil_twin_root`? `secc_wildcard_san`? a non-critical KeyUsage?), the SLAC/SDP
layers supply the lower-layer checks, and `SecurityResearch.md` is effectively the test-case
backlog (CVE-2025-12357 SLAC-MitM, Brokenwire, downgrade, PnC relay-billing). Constrain it to
chargers you are authorised to test — see the ethics note below.

**2. 🏆 Three-way meter verification** (§4.3). EV model vs signed SECC `MeterInfo` vs OCPP
`MeterValues` from your own CSMS. Two independent signatures, one phone, one verdict. The
Eichrecht-at-the-point-of-consumption argument.

**3. Crowd-sourced charger behaviour database.** Anonymised handshake fingerprints — which
protocol versions, suites, services, quirks each charger model exhibits. The 15118 equivalent
of a browser-compat table. Turns every user session into interop data, and the C# stack has
already documented ~12 Josev bugs, so you know exactly how valuable that shape of data is.

**4. Session time-travel debugger.** Record every session as an event log; scrub back and
forth; re-decode any frame; fork the recording and replay it against a live SECC with one
field mutated. Combines Phase 6 with §6.3 and makes conformance bugs reproducible instead of
anecdotal.

**5. Signed complaint receipts.** When the EV's and station's meters disagree beyond a
threshold, generate a signed, self-contained deviation report — both signed readings, both
chains, verification result — that a user can actually send to the CPO or the Eichamt. Turns a
protocol curiosity into consumer leverage.

**6. Live tariff visualisation.** Plot the signed `SalesTariff` / `AbsolutePriceSchedule`,
show the cheapest window the EVCC picked, show the resulting `ChargingProfile`, and show what
it *would* have cost under the alternatives. The stack already verifies real MO-signed tariffs;
the missing half is purely presentational.

**7. Swarm mode.** One phone impersonating N EVs against one SECC / one CSMS — load and
concurrency testing from a device in your pocket.

**8. Teaching mode.** Step through a session message by message with the spec requirement IDs
([V2G2-xxx] / [V2G20-xxx]) shown next to each decision, and the EXI bits highlighted as they
are consumed. The repo already cites requirement IDs throughout; surfacing them is mostly
plumbing, and there is genuinely no good way to learn this protocol today.

**9. NFC "virtual plug".** ✅ *The QR half of this is now a core feature, not an idea — see
§4.5.* What remains speculative is the **NFC** carrier: the same payload as an NDEF record on a
tag stuck to the Pi, so you *tap* instead of scan. Closer still to the feel of plugging in, and
on Android it can launch the app straight from the tap. iOS background tag reading works too,
with tighter constraints. Cheap once §4.5's payload parser exists — the carrier changes, the
payload doesn't. BLE advertisement is a third carrier worth a thought for "walk up and it's
already there" discovery.

**10. EEBUS bridge.** You maintain `WWCP_EEBUS` (its own repo — was briefly staged here, now
removed). A phone that is simultaneously an ISO 15118 EV and an EEBUS EVSE/CEM endpoint could
demo the home-energy handoff — 15118 to the wallbox, EEBUS to the HEMS — which is exactly where
the two standards meet and almost never gets shown end to end. If that story ever matters here,
re-add it as a submodule; it is deliberately *not* a dependency of this app.

> **Ethics / authorisation note for §7.1, #3, #4 — sharpened by the app-store decision (§8).**
> The app ships to the public stores as an **educational / debugging tool**, and its only intended
> counterpart is a Pi you own (real chargers are out of scope, §8). That framing is also the
> compliance boundary: the Scorecard, the crowd database, and the fork-and-replay debugger cross
> from "simulate my own EV" into "probe someone else's infrastructure", and `WWCP_ISO15118`'s own
> `SecurityResearch.md` / `SLAC_Pentests` set the tone — these are research tools. So the
> active-attack surface (the `Evil/` factory beyond your own wallet, SLAC MitM, Scorecard against
> third-party infra) must be **absent from the default store build**, reachable only in an explicit
> authorised-target mode, and never run against infrastructure you don't own or have written
> permission to test. A store reviewer must be able to see a clean, benign default surface.

Most of the first-draft questions are now decided (2026-07-29); recorded here so the reasoning

**Decided:**

3. ~~SDP / V2GTP — whose?~~ — **Vanaheimr's** (§8.3-as-was; now folded into A4/B0). WWCP's stay

4. ~~DIN 70121~~ — **out for now, kept on the optional to-do list** (§6.1). `WWCP_DINSpec` ready.
5. ~~Real chargers~~ — **out of scope.** They speak PLC (no phone PLC, §3.6) and bring the TLS
   (§3.3) and multicast (§3.2) problems; the Pi is the only counterpart. This is what makes the
   controlled-counterpart resolutions in §3.2/§3.3 valid, and it draws the §7.1 authorisation
   boundary.
6. ~~UI framework~~ — **standalone, no Chargy component reuse for now.** (Revisit only if the
   Chargy transparency endgame, §4.3, later argues for shared components.)
7. ~~Distribution~~ — **public App Store / Play Store, as an educational/debugging tool.** Hard
   consequence: the security-research surface must be off by default (see the ethics note above);
   and on iOS, v1 ships in relaxed-TLS mode to avoid a bundled crypto lib in the first store
   build (§3.3).
8. ~~Pairing UX~~ — **QR scanning is a core feature** and the app's central bootstrap concept,
   replacing plug-in + SLAC + SDP; the payload carries **metadata, not just an endpoint**,
   including the transport/crypto profile and its non-conformance reason (§4.5). The codes are
   **dynamic (TOTP)**, reusing `OpenChargingCloud/DynamicQRCodes` (AFIR / OCPP v2.1) — which makes
   the pairing a genuine **proximity proof** and therefore a substitute for SLAC's security role,
   not just its UX (§4.6). Verified Tier-1, in the pairing step before the V2G session.

10. **Swift crypto path (§3.3).** ~~Confirm early whether CryptoKit suffices.~~ **Confirmed by A6
    (2026-07-30): it does not, and the gap is narrower and harder than written.** Narrower, because
    P-521 signing works natively and the entire codec, fragment and dispatch layer never needed
    Ed448 at all — so this no longer threatens the Option-B fallback, which was the original worry.
    Harder, because CryptoKit lacks the *curve*, not a provider registration, so there is no
    equivalent of the JVM's "add BouncyCastle" move.
    **The implementation is chosen and now vendored (2026-07-30): libgoldilocks, in
    `swift/Sources/CGoldilocks`, under our own `V2GEd448` surface.** It arrived through the
    `swift-goldilocks` package, which a spike measured rather than read the README of
    (`swift/SPIKE-ed448.md`); the package dependency was then dropped in favour of checking the
    code in. What decided it:

    | | |
    |---|---|
    | RFC 8032 §7.4 | reproduced **byte for byte**, all eight empty-context vectors |
    | Machine code | **~81 KB** (63 KB C + 18 KB Swift) — against megabytes for OpenSSL |
    | Licence | MIT throughout, notices carried in-tree |
    | Build | no network, no external toolchain, no script phase |

    Two provenance corrections, both found by looking rather than by reading:

    - It is **not pure Swift**, as Swift Package Index bills it — it is C with a thin wrapper.
      That is the better outcome (established field arithmetic rather than fresh crypto), but it
      costs this document's §2 claim of "no runtime to bundle" a footnote: C sources in a SwiftPM
      build are far smaller than a bundled runtime, and not nothing.
    - It is **not Mike Hamburg's library**, which is what this section said for a day. The chain is
      Hamburg's libdecaf (2014–2016) → forked 2018 by the OTRv4 project as `otrv4/libgoldilocks` →
      a Swift-facing C shim → the package. A community fork with years of drift is a weaker pedigree
      than "the reference implementation", which was the argument for not writing our own. It does
      not reverse the decision — the vectors pass, and no alternative has a better pedigree — but
      the claim needed correcting, and it only surfaced when the code was read as *ours*.

    **Vendored rather than depended upon**, which was the hedge this section listed as optional and
    is now done: nobody's release cadence sits between us and the code that makes our signatures,
    the licence notices travel with the source, and RFC 8032 §7.4 is the acceptance test any future
    replacement has to pass.

    **Wired into all five -20 sets the same day.** `V2GSignature` in CommonMessages, AC, DC and both
    DER sets now signs and verifies Ed448, each over its own fragment — ACDP is the exception, as it
    has no signable element. `ed448NotAvailable` is gone; the errors that replaced it say something
    a caller can act on: `unsupportedAlgorithm(String)` and
    `algorithmMismatch(declared:attempted:)`.

    Two things fell out of the integration that are worth recording:

    - **The dispatch fix came with it.** Every entry point reads `SignatureMethod/@Algorithm` and
      refuses to act against it, replacing a guess from the signature length. That guard is what
      makes `#eddsa-ed448ph` a named refusal rather than a message signed under the wrong variant.
    - **Ed448 keys are per-set types**, because the sets are separate modules — a wallet holding one
      key converts between them. Cheap and lossless (the seed is the whole key), but real friction,
      and it follows from the same independence that forces five `V2GSignature` copies.

    Still orthogonal to the transport-TLS half of §3.3, which this does not touch, and deferrable
    regardless (§8 #7: v1 ships relaxed).

    **The algorithm parameters are now settled (2026-07-30), and the acceptance test exists.**
    ISO 15118-20 uses `http://www.w3.org/2021/04/xmldsig-more#eddsa-ed448`, which RFC 9231 §2.3.12
    lists separately from `#eddsa-ed448ph` — so **pure Ed448, not prehashed**, signing the SignedInfo
    fragment octets directly with no external digest (SHAKE256 inside the algorithm does that job),
    114-byte raw signature, **empty context**.

    Two caveats worth carrying, because they bound how much that sentence is worth:

    - **The empty context is the one part no RFC states.** RFC 8032 §5.2 gives Ed448 a context of up
      to 255 octets and §7.4 includes a `"foo"`-context vector that shares its key and message with
      the empty-context one and produces a completely different signature. RFC 9231 is silent. Empty
      is conventional and near-certainly right, but it rests on the ISO text, which is paid and not
      in the repository. If a peer ever rejects our Ed448, this is the first thing to re-read.
    - **Until 2026-07-30 the Ed448 path had no oracle at all** — three self-referential tests, and
      no live-interop evidence, because the -20 secp521r1/Ed448 profile is one Josev cannot
      exercise. Cross-checking Swift against C#, as originally planned, would have inherited that
      assumption rather than tested it.

    So RFC 8032 §7.4's nine published vectors are now checked in
    (`Vanaheimr.V2G.Exi.Tests/Vectors/Ed448.rfc8032.vectors.json`, extracted mechanically by
    `tools/rfc8032-ref/`) and run against both back ends. **That corpus is the acceptance test for
    whichever library is chosen**: a candidate reproduces the standard's own signatures byte for
    byte, or it is not a candidate. It also settles the API question that prompted the search — a
    library with no context parameter expresses empty-context pure Ed448 exactly, which is what we
    need, and cannot express `#eddsa-ed448ph`, which we do not.

12. ~~**QR payload schema freeze (§4.5/§4.6).**~~ **Frozen as v1 (2026-07-30)** — implemented,
    tested and documented in `pairing/` (see its README for the field table). The V2G additions are
    `host`, `port`, `tp`, `proto`, `crypto`, `nc`, `ncwhy`, `root`, `meter`, `wifi`; the OCPP v2.1
    names are reused verbatim. `sig` did **not** land in v1: it only pays off once the app already
    trusts a root, and `root` covers the bootstrap case it was wanted for.

    Three decisions the implementation forced, each now pinned by a test:

    - **Unknown parameters are carried, never dropped or rejected.** A newer Pi must talk to an
      older app, and a reader that discards what it cannot understand also cannot warn that it was
      there. Nothing interprets them, which is what makes carrying them safe.
    - **A repeated parameter is refused rather than resolved.** "First wins" and "last wins" are
      both defensible, and a hostile code only needs the confirmation sheet and the connector to
      disagree about which.
    - **Absent `crypto` warns exactly like a weakened one.** Silence is not conformance, and it is
      the cheapest thing for a hostile code to offer.

    Still worth doing: checking whether the V2G additions interest OCPP v2.1 itself.
